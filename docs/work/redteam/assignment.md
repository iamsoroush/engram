# Red-team report: capture→patient-assignment pipeline

> Verbatim agent report, 2026-07-05. Scope: `apps/backend/app/services/ai_jobs/{worker,intents,orchestration,recovery,reports,context}.py`, `services/{patient_matching,patient_assignment_timeline,captures,capture_storage,sessions,patients,patient_memory}.py`, `apps/ai_engine/ai_engine/jobs/{capture_audio,capture_note,capture_photo}.py`, `prompts/transcription.py`, against `docs/intelligence-layer.md` §4–5. Excludes the already-diagnosed incident cluster. Ranked by severity.

## Tier 1 — clinical-harm

### A-F1. [T8] Out-of-order capture arrival double-dispatches the chain → concurrent same-session completions, lost assignment events, arbitrary final patient — CONFIRMED-IN-CODE
The "captures process strictly in order" invariant is enforced only against jobs that already exist. `is_capture_chain_head` (orchestration.py:178–196) checks whether this job is the *earliest in-flight* job — it does **not** check whether another job is currently running. Upload dispatch (capture_storage.py:409–415) dispatches whenever the new job is head. So: capture 2 (10:02, small file) finishes uploading first — its job is the only one, dispatched, running. Capture 1 (10:00, long audio, slow upload) lands — its job is created, `captured_at` is earlier, so it *is* the head → dispatched immediately **while job 2 is still running**. This is deterministic, not a narrow timing race. The manual reprocess path is worse: `enqueue_capture_processing_job` (orchestration.py:637–654) dispatches with no head check at all.
Two `complete_worker_job` calls for the same session then interleave: both read `session.extracted_metadata`, both see `patient_id is None` → both take "first identity wins" (worker.py:497–545) → two patients matched/created, and since there is no row locking anywhere (`with_for_update` appears nowhere in the backend) the whole-column JSONB write means the last committer **erases the other capture's timeline event** — no chip, no undo, no trace; the loser's `ai_patient_action` still claims success in job metadata.
- Scenario: two captures naming Sara and Maryam upload out of order → final assignment is commit-order lottery; one assignment event and possibly one ghost patient with no visible basis.
- Fix direction: dispatch at upload only via `dispatch_next_session_capture` (which does check running), and serialize completion per session (advisory lock / `SELECT … FOR UPDATE` on the session row).
- Golden case: integration test — enqueue job B, start it, then create earlier-captured A; assert A is not dispatched until B completes.

### A-F2. [T8/T7] Staff reassignment while synthesis is in flight is silently reverted — CONFIRMED-IN-CODE (structural)
`complete_session_worker_job` loads the session at start (worker.py:868–871), snapshots `previous_metadata` (worker.py:947), and at the end **wholesale-rewrites** `session.extracted_metadata` (worker.py:1044–1067). A staff reassignment committing during the job (sessions.py:526–536 — read-modify-write on the same column, also unlocked) has its timeline event clobbered, while `session.patient_id` (which synthesis never writes) keeps the new patient. Result: `patient_id` = Patient B, timeline's latest event = Patient A. The *next* `apply_active_patient_assignment` (any capture delete, any AI assignment) recomputes from the timeline and **flips the visit back to Patient A**. Meanwhile safety flags sync onto whatever `session.patient_id` says at completion (worker.py:1071–1079).
- Fix direction: at completion, re-merge timeline keys by event id under a row lock instead of overwriting; treat `patient_assignment_timeline` as append-only.
- Golden case: start synthesis, reassign mid-flight, complete job → assert staff event survives and patient stays B after a subsequent `apply_active_patient_assignment`.

### A-F3. [T7] Reassignment never refreshes the synthesized report — the new patient inherits the old patient's carried-forward treatments — CONFIRMED-IN-CODE
`assign_session_patient` only stores an escalation *hint* (sessions.py:581–582 → `mark_synthesis_escalation`); it never dispatches or forces anything. `maybe_dispatch_session_synthesis` requires an uncontributed capture or `force` (reports.py:445), and the deterministic floor early-returns because the content signature (reports.py:72–80) hashes **capture ids + text only — not patient_id** — so `report_synthesis.status == "current"` holds (reports.py:304–312). The synthesis was built with `bounded_prior_visit_treatments` of the *old* patient (worker.py:336, 907): its carry-forwards, prior-visit references, and `treatments[]` in `extracted_metadata` now sit on a visit filed under the *new* patient, feed the new patient's memory job, and the session reads "complete". Nothing marks the report stale.
- Scenario: visit auto-filed to wrong Sara → report says "carried forward: Botox 20u from previous visit" (Sara's history) → staff reassigns to Maryam → report and treatments store keep Sara-derived content indefinitely.
- Fix direction: on reassignment of a session with a current synthesis, force a re-dispatch (the escalation hint already exists — pair it with `maybe_dispatch_session_synthesis(force=True)`), or fold patient_id into the signature.
- Golden case: eval/integration — synthesize with prior-visit carry-forward, reassign, assert report regenerates without old-patient carry-forwards.

### A-F4. [T1/T4] Out-of-context does not veto identity assignment — an OOC capture can file (or create!) the patient — CONFIRMED-IN-CODE
In `complete_worker_job` the identity/assignment block (worker.py:487–607) runs unconditionally; the `out_of_context` marker is computed *afterwards* (worker.py:618–620) and never consulted. The prompt extracts `patient_information` independently of OOC. So "یادم باشه به خانم کریمی زنگ بزنم" ("remind me to call Ms. Karimi") on an unassigned visit → model flags OOC *and* extracts Karimi → first-identity-wins assigns the visit to Karimi — or `no_match` **creates** a Karimi patient — then the same capture is dimmed and excluded from the report. There is also no reverse path: staff can only clear OOC (`update_capture` coerces any incoming `out_of_context` to `present: False`, captures.py:53–64); marking a capture OOC after the fact has no code path at all, and only capture *deletion* de-effects an assignment.
- Fix direction: when `out_of_context.present`, downgrade any identity effect to a suggestion; add a staff "mark out of context" path that de-effects like deletion (reuse the timeline's valid-event filter).
- Golden case: eval fixture — non-clinical audio naming a third person → expect no assignment/creation, suggestion at most.

### A-F5. [T4/T1] National-ID match short-circuits with confidence 1.0 and never cross-checks the spoken name — CONFIRMED-IN-CODE
The ladder returns `decision="matched"` on a national-ID hit immediately (patient_matching.py:315–332) with no consistency risk against the *also-spoken* name. `_national_id_conflict` only guards the reverse direction (name/contact match contradicted by a provided ID, patient_matching.py:254–270). Persian IDs are dictated digit-by-digit (prompt, transcription.py:30); one ASR digit error that happens to collide with another patient's stored ID reassigns/creates with full confidence — under explicit basis it auto-applies even at `strict` strictness (deterministic match), producing a wrong-chart write whose only defense is a human noticing the chip.
- Fix direction: when extracted name similarity against the ID-matched patient's aliases is very low, add a risk and demote to `possible_match` (routes to resolver at every strictness).
- Golden case (eval-worthy): patient_information {name: "Sara Ahmadi", national_id: <Maryam's ID>} → expect `possible_match` + conflict risk, not `matched`.

### A-F6. [T7/T2] Fix-at-source transcript edit never re-runs matching — corrected transcript, wrong patient stays — CONFIRMED-IN-CODE
`update_capture` on a transcript edit (captures.py:70–76) only marks the report stale + escalation and harvests feedback. The `patient_information`, match candidate, and any assignment the *mis-transcribed* name drove are untouched. Cross-surface inconsistency: the capture card shows the corrected name; the session header, patient page, and memory show the wrong patient. The system's own recommended correction gesture (edit-at-source) does not correct the one effect that matters.
- Fix direction: if the edited transcript changes the extracted name span, re-run matching and surface a suggested reassignment chip.
- Golden case: assign via misheard "معاضد", staff edits transcript to "معاصد" → expect a reassignment suggestion.

## Tier 2 — trust

### A-F7. [T1/T8] Failed captures don't hold the chain, and a recovered older capture's assignment is applied-but-inert — CONFIRMED-IN-CODE
Chain head considers only queued/running jobs (orchestration.py:189–196), so a failed head lets later captures assign first. When the older job is requeued (`requeue_failed_session_captures`, worker.py:672–675) and completes, its event's `effectiveAt` is its `captured_at` (worker.py:174) — older than the later capture's event — so latest-valid-wins (patient_assignment_timeline.py:148, 158–166) ignores it. The job succeeds, `ai_patient_action` says "assigned", audit logs completion — but nothing changed and no conflict surface appears. A T1 silent cell created purely by ordering.
- Fix direction: after `apply_active_patient_assignment`, if the just-appended event is not the active one, emit a suggested-reassignment/conflict chip instead of nothing.

### A-F8. [T2] Notes and photos have zero identity/assignment semantics — modality asymmetry — CONFIRMED-IN-CODE
`text_capture_process` is a pure passthrough (capture_note.py contains no `patient_information`/`intents`), and photo output carries only `out_of_context` (capture_photo.py:123–136). A typed note "بیمار را عوض کن به مریم رضایی" or a photographed intake form with name + national ID produces no match, no suggestion, no notice — while the identical spoken sentence reassigns the visit. Users who learn the audio behavior will reasonably expect the note to work.
- Fix direction: run the same intent/identity extraction over note text (deterministic regex for IDs/phones at minimum, LLM for Pro); at least surface a suggestion. Photos: keep captions neutral but consider an identity-visible flag routed to needs-input.
- Golden case: note fixture with explicit reassignment text → expect suggestion effect.

### A-F9. [T2] No unassign / negation semantics from capture — CONFIRMED-IN-CODE
"این پرونده مال خانم قاسمی نیست" / "wrong patient, remove her" carries no name/id/phone/email → `patient_information_has_explicit_identity` is false (patients.py:170–172) → the entire intent block is skipped (worker.py:491–494). The schema (intelligence-layer.md §4) cannot even express detach-without-replacement; only manual `manually_unassigned` exists (sessions.py:528).
- Fix direction: add a `detach`/negation intent to the schema; map to a suggested unassign (never silent).

### A-F10. [T5] Synthesis start/recovery stomps the session to `processing`, and the skip path strands it there — CONFIRMED-IN-CODE
`stop_recovery_if_target_is_gone` unconditionally sets `session.status = processing` for session-level jobs (recovery.py:168) and is called on **every** `start_worker_job` (worker.py:395) — defeating the "quiet enrichment, no processing flash" guard four lines below (worker.py:426–431). Worse, `_complete_session_synthesis_skip` (worker.py:801–855) never restores the status, and terminal failure with a baseline report deliberately skips status changes (worker.py:1195–1208). Net: a Pro tenant whose gateway skips or dies gets sessions stuck in `processing` with a complete visible report and no reachable resolver until an unrelated capture/edit triggers a regen.
- Fix direction: in the session branch of `stop_recovery_if_target_is_gone`, set `processing` only when no report sections exist (mirror worker.py:429–431); skip/terminal paths restore `needs_review`/`unassigned`.

### A-F11. [T7/T5] The contract's "Needs-input item" for suggested reassignments doesn't exist, and Dismiss is device-local — CONFIRMED-IN-CODE
`docs/intelligence-layer.md` §7 promises "a `Suggested: reassign to N` chip (and a Needs-input item)". The needs-input builder (`_session_needs_input_item`, patient_memory.py:167–219) has exactly four kinds — none covers a suggested reassignment on an *assigned* visit, and the AES-906 policy-deferred suggestion "routed to the owner" has no owner-facing surface at all beyond scrolling that session's capture cards. Additionally the chip's Dismiss is pure React state (`CaptureBadges.tsx:162–181`) — it reappears on every reload and other devices, and is never recorded as a decision.
- Fix direction: add a `suggested-reassignment` needs-input kind (owner-scoped when `policyDeferred`); persist dismissal into capture metadata (also a feedback-harvest signal).

### A-F12. [T1] Explicit reassignment to an unmatched, uncreateable identity dies silently — CONFIRMED-IN-CODE
Explicit basis + `no_match` + creation refused (`create_patient_from_patient_information` returns None when there's no display name — phone/ID-only identity, patients.py:238–240) → `resolve_ai_patient_from_match` yields nothing, `fuzzy_auto_apply_candidate` and `near_match_suggestion` both require `decision == "possible_match"` (intents.py:250, 211) → no assignment, no suggestion; just a raw `no_match` dict in capture metadata that renders no actionable chip (CaptureBadges keys on `suggested_reassignment`). On an assigned visit the wrong patient silently stays despite an explicit spoken correction.
- Fix direction: explicit basis that produced no effect → always emit an actionable "couldn't apply — assign manually" suggestion carrying the spoken identity.

## Tier 3 — cosmetic / speculative

### A-F13. [T6/T7] Stale session-level match candidate + needs-input key mismatch — CONFIRMED-IN-CODE, cosmetic
`patient_match_candidate` written to session metadata while unassigned (worker.py:645–647) is never cleared by `apply_active_patient_assignment` (strips other keys only, patient_assignment_timeline.py:189–193) nor by staff assignment without a basis capture (sessions.py:540–546 clears only the capture copy). Related: `_session_needs_input_item` reads `patient_match` (legacy session-job key, patient_memory.py:187–189) while the capture pipeline writes `patient_match_candidate`, so ambiguous/conflict matches on unassigned visits demote to the generic "assign-patient" item instead of "choose-patient"/"resolve-conflict".

### A-F14. [T4] Two names / in-clip self-correction in one audio — SPECULATIVE (prompt evidence)
The schema holds exactly one `patient_information` and the prompt (transcription.py:33) gives no rule for a clip containing two candidate names or a mid-sentence correction ("برای سارا… نه، مریم"). Which name wins is model roulette; no uncertainty routing exists for "multiple identities heard". Golden cases: (a) self-correction → expect the corrected name + explicit basis; (b) two distinct patients mentioned → expect low confidence/uncertainty, suggestion not application.

### A-F15. [T4] A pure assignment-correction clip matches the out-of-context definition — SPECULATIVE (prompt evidence)
"Set out_of_context.present=true when the audio has no clinical or visit content" (transcription.py:33): a clip that *only* says "wrong patient, it's Sara" has no clinical content — the prompt invites OOC on the correction itself. Combined with A-F4 the assignment still applies but the capture gets dimmed with contradictory chips; if the model emits OOC *instead of* assignment, the correction dies. Prompt needs a carve-out: assignment/administrative instructions ARE visit content.

### A-F16. [T8/T6] Duplicate patient creation across concurrent sessions / staff-vs-AI create — SPECULATIVE
AI `no_match` creation (worker.py:204–212) never consults `find_patient_duplicates` (that guard is staff-create only, patient_matching.py:426+), and capture chains are per-session — two sessions naming the same new patient in the same window, or front-desk staff creating the patient while the AI job is in flight, produce duplicates that the AES-205 guard was built to prevent. Fix direction: run the duplicate guard inside AI creation; on a strong hit, suggest instead of create.

## Cross-cutting root causes
1. **No concurrency control on `session.extracted_metadata`** — the timeline is event-sourced but stored/written as a single clobbered JSONB column with no locks (A-F1, A-F2).
2. **Ordering is assumed, not enforced** — chain-head logic ignores running jobs and failed heads; `effectiveAt = captured_at` makes late completions silently inert (A-F1, A-F7).
3. **Assignment effects have no invalidation edges** — reassignment, OOC marking, and transcript edits all change the *inputs* to an applied assignment/synthesis without re-evaluating it (A-F3, A-F4, A-F6).
4. **"Explicit intent must never no-op silently" is not an invariant** — several lattice cells (A-F7, A-F12, A-F9, A-F8) end in success-shaped silence; a completion-time assertion ("explicit basis ⇒ an effect or a suggestion was written") would catch the whole class, and is the cheapest single guard to add.
